# 全链路验收缺陷修复与定向复验

本轮保留原验收失败记录，分两个冻结版本修复并复验。完成的是已定位缺陷的工程修复与定向验证，不是重跑全部 12 场景后宣布整体通过。

## 修复内容

1. **待确认申请的多轮继承**：Sessions 历史读取加入 WAITING_CONFIRMATION，保留已有 goal 和对话上下文；不继承待执行 pending 动作，旧确认仍由版本/参数校验阻断。
2. **已办理请求的衔接**：从真实持久化模拟工单回执关联唯一的 active service.apply，保存 fulfilled_business_goals。它是业务回执记录，不擅自把所有意图改为完成；后续查询不再被已办理申请阻塞，也不能重复办理同一已履行诉求。
3. **意图和工具诊断**：受控原因码、schema 字段路径/类型进入事件；不记录模型原值、异常上下文、凭据或未知字段原名。原文依据非法明确记录 INTENT_EVIDENCE_INVALID。
4. **一次受限结构修复**：意图结构或依据校验失败时，预算足够才允许一次模型纠正；第一次不更新状态，第二次仍严格校验。不重试传输 RuntimeError/超时，不增加总预算。直接 understand 调用默认不修复，真实 Agent 显式按预算启用。
5. **视觉需求传递**：Delta 增加 visual_request 与原文依据，识别明确原图/位置需求和上传对照；区分内部 AI 专家与人工，不因“排查专家”自动新增人工诉求。
6. **真实读图与预算**：上传对照先观察已授权照片，再由主控判断差异；明确原图请求在预算内检查授权资产。有已检查图片及证据时最多一次直接进入最终化，减少重复规划/观察耗尽 token；失败后仍回到正常修复路径，不无限重复同一捷径。
7. **缺图状态**：明确要求图片但未能展示时保留 partial 与缺口提示，图片文件不可用有告警；不伪造替代图，也不忽略语义核验。
8. **混合问题核验范围**：已有业务查询结果时，只有所有剩余手册目标都能对应本轮已校验原文片段，才将这些片段作为手册子问题。完整原问题和独立业务上下文仍传给 Writer/Verifier；无法可靠分解则保守使用原问题。
9. **正确订单项**：主控输入新增当前用户、当前商品/型号的真实订单项，明确 related_order_item 不能用 product_id。提交前校验订单项，避免反复把商品 ID 当成订单 ID；原确认与订单范围检查保留。

## 两轮真实结果

第一轮 `artifacts/shopguide/customer-repair-v1/`：9 条用户消息、57 请求。暂停保留同一目标成功；首次原图场景 answered，实际 4 个图像输入；混合查询/指南通过核验；上传图片对照实际读图并指出 TEST-DS2 与当前 TEST-DS 不符。仍失败：撤回的原文依据非法、图片追问耗尽 token，以及办理时模型误用商品 ID。这些结果未被第二轮覆盖，第一轮源码另有 frozen-source.tar.gz。

第二轮 `artifacts/shopguide/customer-repair-v2/`：5 条消息、19 请求，核对结果如下：

| 场景 | 结果 |
|---|---|
| 同一暂停申请撤回 | 原 g1 从 suspended 变为 withdrawn，未恢复办理；但仍返回了此前指南内容，撤回确认文案有待完善 |
| 原图追问 | 3 次模型调用、4 个图像输入，answered 且返回登记资产；比第一轮耗尽预算的结果改善，不外推为性能指标 |
| 创建并查询模拟工单 | 进入确认，用户确认后提交成功；查询返回的 ticket_id 与新回执严格一致 |
| 只咨询是否免费 | 识别为规则咨询，policy 子 Agent 实际检索；没有费用资料，拒绝承诺免费，未创建工单。用户文案仍可简化 |

浏览器只读检查验证最后一条原图答复加载、移动端无横向溢出，不产生模型调用。最初检查脚本误用 .exchange:last-child 导致超时，修正 DOM 定位后另存结果，不将脚本定位问题当作产品读图失败。

本轮共 76 次请求，累计 **1046/1158**，剩余 112；语义纠正、失败和所有角色调用均计入，未超额度。没有重新进行全部 12 场景或正式 PM209/ECom 评测，也未接真人客服或真实商家后端。
