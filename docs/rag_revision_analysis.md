# 意图候选检索与 RAG 改造需求分析

本记录分析用户提供的“多路粗判→候选融合→精排→上下文判决”方案，并映射到当前代码。对应 PLAN §8.7–8.11、§12.10 和 IR 测试矩阵。**本轮仅更新计划，没有实现、训练、建库或真实模型调用。**

## 关键判断

附件主要解决“用户想做什么”，输出是意图和槽位；现有说明书 RAG 解决“哪些资料能支持回答”，输出是证据和原图。应作为两个相连的检索层，不能把意图样例、说明书、业务查询记录混成一个库，也不能用意图识别准确率证明指南正确。

已确定的主从 Agent 保留。前置意图 Judge 更新多诉求状态，由主控决定委派或调用业务工具；子 Agent 继续在授权资料范围内检索。工单状态来自业务查询工具，人工交接仍暂停。

## 当前代码与缺口

| 位置 | 已有能力 | 新需求缺口 |
|---|---|---|
| intent/taxonomy.json | 六类意图，定义、正例和排除边界 | 关键词/负模式/槽位规范、完整样例集与训练版本 |
| intent/service.py | 一次 LLM 理解、Delta 校验和多 goal 状态 | 多路候选、融合、意图精排、逐层可观测性 |
| retrieval/store.py | 授权 dense/FTS、RRF、重排与证据结果 | 独立意图样例 namespace；改造不能替换现有证据权限链 |
| retrieval/models.py | 真实 BGE 和重排适配；显式 fake 测试组件 | 没有已训练 BERT 意图分类器或经验证的意图专用精排模型 |
| qa/fixed.py | 页面聚合、证据预算、图片观察和最终核验 | 先拼页再截前 32 条、候选图片前四张的偏置仍需处理 |
| agent/runtime.py | 意图、主从委派、共享预算、独立工单结果 | 接入候选增强时不能额外复制整条 Judge 或改变业务授权 |

## 采纳与调整

| 附件设计 | 项目处理 |
|---|---|
| Keyword、BERT、Embedding、Slot 多源候选 | 纳入目标架构，按数据与模型就绪程度分阶段接入；未训练分支显式关闭 |
| 正负关键词 | 保留原文依据；否定、撤回与咨询边界必须结合上下文，不能全局排除词命中的类别 |
| BERT 单标签 softmax | 仅能作分支基线；首版多诉求需要多标签或按诉求分段，不能覆盖现有多 goal |
| 加权融合与相似度聚合公式 | 作为实验初值；需处理分数尺度、少样例、缺失分支与校准，不声称最佳参数 |
| Top3–5，再精排 Top3 | 可调召回预算；增加状态保留项、多诉求分组和未知出口，防止正确目标被截掉 |
| Context 只在最后出现 | 保留末端 LLM 联合判决，但候选阶段也补充已存在/被引用目标；否则最后可能没有正确候选可选 |
| 单一 active_intent | 不采纳为状态存储；保留当前独立 goal、暂停/撤回/恢复及来源历史 |
| LLM 自报 confidence | 不能当正确概率或执行授权；有标注验证后才选拒识/澄清策略 |
| 自动 hard negative | 可生成待审候选，多标签和重叠定义中“不是主标签”不必然是负样本 |
| 无人工在线闭环 | 在线分类可自动进行；离线数据/目录审核及用户对业务操作的确认不能取消 |
| 物流、发票、真实退款示例 | 仅作方法说明，不隐含增加业务系统或个人信息采集；当前仍以已确认八项客服范围为准 |

## 推荐实施顺序

先冻结意图库/标注规范和输入输出，再做规则、样例召回与槽位特征，测候选是否保住全部目标。随后加融合与精排，将结果交给现有 LLM/reducer。BERT 与专用 Cross-Encoder 训练需要独立数据准备、审核和权重登记，不在空数据下搭“假四路”。目前只有六类意图，应保留全目录判决作为参照，避免以缩小候选本身当作收益。

资料 RAG 单独优化页面/区域/图片预算，在相同证据和视觉预算下观察实际进入上下文的相关资料是否更多；不能使用 gold 来决定取舍。意图层和文档层分别冻结配置、评测与报告，主从结构不作为重新选择项。

验收先看候选召回和状态保留，再看最终意图/槽位、未知/澄清和客服任务成功；文档侧另看证据召回、实际上下文、原图与回答正确性。训练与测试按完整会话及近似改写分组，未使用的真实测试集不能用来调候选和融合权重。

该方案比当前六类目录的一次 Judge 增加了本地模型、训练数据和调试成本，收益目前未知；计划保留分支开关与分层诊断，要求每个启用分支都能说明来源、实际执行状态和成本。所有新增任务保持未勾选。

后续执行：首阶段候选管线已落地，见 [实现与验证记录](intent_candidate_implementation.md)；本文“仅计划”为需求分析阶段状态。完整 RAG 改造仍未完成。
