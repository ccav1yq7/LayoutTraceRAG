# 模拟工单查询

已实现 `query_service_requests`，通过现有 Agent 消息入口调用，无新增业务写接口。人工交接按用户要求暂不实施。

- 可传精确 ticket_id；未传则列出当前用户、当前商品及型号的工单。
- 查询先认证 run/session，再核对用户当前订单项；非 demo 域拒绝。他人工单、其他商品/型号工单与不存在编号统一返回无可查看记录，不泄露其存在性。
- 数据来自 sg_tickets；该表仅记录创建，没有派单/维修/完成状态，因此只显示“模拟工单已创建”，明确未接真实维修进度。
- 最多返回 20 条，另查一条判定 has_more；排序按编号稳定排序，不声称按时间最新。超过上限提示提供编号；不按数组首项猜测用户所指工单。
- 查询是只读动作，不需要办理确认，也不触发准备/提交工单。业务结果直接展示，不经说明书 Writer 生成状态。
- 前端展示编号、摘要、创建状态及无记录/超量提示；已创建工单有“查询此工单”按钮，填写当前输入框，由用户发送。刷新可从持久 run 恢复查询结果。
- 规划提示升级 agent-v5；WebDemoGateway 仅为显式 fake 演示增加查询分支，不能将其测试结果当作真实意图识别效果。真实 Agent 使用现有 intent/plan 工具选择，未进行本轮真实模型复测。

入口示例：“查询工单”“查询工单 ticket_…”。完整链路是准备→用户确认→提交→同编号查询。已保留原权限、确认、取消与执行账本逻辑。

验证证据：`artifacts/shopguide/service-query-regression.xml`（后端）、`artifacts/shopguide/service-query-browser.txt`（浏览器）。前端构建、2 项单元测试及 Ruff/Mypy 另行检查。本轮没有调用真实模型，总请求账本不增加。

边界：没有真实维修状态同步、客服坐席、人工更新后台或自动推送；没有擅自给既有工单补造时间线。多诉求中查询结果与其他问答的统一编排仍属于 FR-15 后续工作。

最终验证：后端 Agent/API/查询共 36 项通过（1 条依赖弃用警告）；浏览器创建→查询→刷新恢复 1 项通过；前端 2 项单元测试通过，构建与 Ruff/Mypy 通过。最初 API 测试读取错误的响应字段 id，已改为现有接口的 run_id 后完成回归，未改变 API 契约。

主从协作后续：当意图状态还包含其他有效诉求时，工单查询结果被保留并继续主控处理，最终可同时展示查询结果与指南回答/澄清；纯查询保持直接返回。该改动不增加工单写操作。
